Git

Keeping the history of a folder, and working on it with other people.

Git is a program that remembers every version of the files in a folder. You tell it when a piece of work is done, and it keeps that state for good, with a sentence from you saying what changed. Later you can look at any earlier state, see who changed a line and why, try an idea without risk to the work that is finished, and share the folder with someone else without mailing files back and forth. It is used most for programs, but it works as well for a folder of recipes, a set of letters or a small website.

Tuatara does not replace git. It runs the git on your computer for you and shows what git says in buffers you can read and act on. Everything starts from one buffer, the status, which C-x g opens. This chapter explains the status first, then the daily round of staging and committing, then looking at history, branches, sharing with a remote, and the tools for finding out when and why something changed.

The examples use a folder of recipes, ~/recipes, with a text file for each recipe. You need git installed, and git needs to know your name once. If you have never used it, type these two lines in a terminal, with your own name and address:

git config --global user.name "Aroha Example"
git config --global user.email "aroha@example.org"

15.1 What git keeps

A few words come up on every page of this chapter. They are git's own, and the same in every book about it.

A repository is a folder whose history git keeps. Git stores the history in a hidden folder called .git inside it. Your files stay ordinary files that any program can open.

A commit is one saved state of the whole folder, with a message, your name and the time. Commits form a chain, each one pointing back to the one before. Every commit has a name of its own made of letters and digits, called its hash, such as 3f9c2ab. You rarely type one; you pick the commit from a list.

Staging is how you choose what goes into the next commit. Suppose you fixed the oven temperature in one recipe and began a new recipe in the same hour. Those are two pieces of work. You stage the fix and commit it, then stage the new recipe and commit that. Each commit then says one thing, which makes the history easy to read a year later. What is staged is kept in a list that git calls the index.

A branch is a line of commits with a name. A new repository has one, usually called main. You make another when you want to try something, such as rewriting every recipe in metric measures, and keep main as it is until the new work is ready.

A remote is another copy of the repository, most often on a server. You push your commits to it and fetch the commits other people pushed.

The keys on the arrows are the ones you press in the status: s stages, u unstages, c c commits, P p pushes and F u pulls. The rest of the chapter takes them one at a time.

15.2 The status

C-x g shows the state of the repository that the current file or folder is in. It is the place you work with git from. It shows the branch you are on, the files that have changed, what is staged, and the latest commits.

The first time you open the status of a project, Tuatara asks whether you trust it, because git can run programs that a repository names. Chapter 12 explains the question and its three answers. For a folder you made yourself, answer y and then type yes.

Figure 15.2 shows the status of the recipes after an afternoon's work.

The first line names the branch and the subject of its last commit. The second appears when the branch follows a branch on a remote, its upstream, and says how many commits you have that the remote lacks (ahead) and how many it has that you lack (behind). When git is in the middle of something, such as a merge that stopped, a third line beginning Doing: says what and which keys go on with it or stop it.

15.2.1 Menus

Most keys in the status open a menu, a small panel that lists what you can do next, each action with a key. c opens the commit menu, and c again there starts a commit, so the whole thing is written c c. C-g closes a menu without doing anything, and C-h in a menu lists every action with its description.

Many menus also have switches. A switch changes how the next action runs, and its key begins with -. In the push menu, - n turns on "Only try", and the push that follows only reports what it would send. An option is a switch that takes a value, and its key begins with =. In the log menu, = n asks how many commits to list.

To keep the menus short, they show the actions used most. ~ in the status switches that status between the short menus and the full ones. When this chapter names an action you cannot see in a menu, press ~ first. To have the full menus always, put this in your init file:

(setf *git-menus* :full)

*git-slim-actions* is the list of actions the short menus show, if you would sooner add one or two than see them all.

  5. Press TAB on the heading Untracked files. The section folds to one line. Press TAB again to open it.
  6. Press q. The status closes. C-x g opens it again whenever you want it.

15.3 Staging

Staging is choosing. s on a file's line moves the file to Staged changes, and u there moves it back. Neither changes the file itself. On a section's heading, s stages every file of the section at once, which is the quick way when all of your changes belong together.

15.3.1 Hunks and single lines

Often a file holds two changes that deserve a commit each. Press TAB on the file and its changes appear under it. Lines that were added begin with +, and lines that were taken away begin with -. The changes come in groups called hunks, each a run of changed lines with a few unchanged lines around it, under a line that begins with @@.

With the cursor on a hunk, s stages that hunk alone. For something finer still, select lines inside a hunk with V and then press s: only the selected lines are staged. u works the same way under Staged changes.

A file with a great many changes shows the first *git-diff-lines* lines of them, then a line saying how many more there are. TAB on that line shows more. Staging the file still takes all of it.

15.3.2 Reversing a change

x throws a change away. On a file under Unstaged changes it puts the file back to how the last commit has it. On a hunk it removes that hunk's change, and with lines selected, those lines. Tuatara asks first and says that it cannot be undone, because git never had a copy of the text you are discarding.

A file that is not tracked is treated more gently. x moves it to the trash, and you can put it back from there (chapter 10).

15.3.3 From the file itself

You do not have to open the status to stage. In a saved file, with the cursor on a changed line, M-x git-stage-hunk stages the change at the cursor and M-x git-unstage-hunk takes it back. M-x git-stage-file and M-x git-unstage-file do the whole file. The same actions are in the file menu, described under Blame and the file menu below.

A file in a repository also shows its changes in the gutter, the narrow strip at the left of the window. There is a mark beside each line added since the last commit, another beside each changed line, and one where lines were deleted. The marks are worked out in the background when the file is first shown and after each save. M-x vc-gutter-mode turns them off everywhere, or on again. M-x vc-gutter-refresh works them out anew, which you may want after a commit made in a terminal.

15.4 Committing

When what is staged is one finished piece of work, commit it. c c opens a buffer for the message, with a list of what is staged under it on lines that begin with #. Those lines are for you to read and are left out of the commit. The buffer starts in INSERT state, so you can type at once.

A good message has a short first line that says what changed, such as Lower the oven temperature for scones. If there is more to say, leave an empty line and write a paragraph on why. The lines are filled at *git-commit-fill-column* as you type.

C-c C-c makes the commit and closes the buffer. C-c C-k gives the message up, and nothing is committed.

Try it, with the recipes

  1. Open the status of ~/recipes with C-x g. Move to scones.txt and press s. The file moves to Staged changes.
  2. Press c, then c. The message buffer opens.
  3. Type Start the recipe folder. Press C-g and then C-c C-c.
  4. The status now has a section Recent commits with your commit in it, and the first line shows its subject.
  5. Open scones.txt, add the line 1 pinch salt at the end and, a few lines up, change 2 cups flour to 3 cups flour. Save with C-x C-s and press C-x g.
  6. Press TAB on scones.txt. Move to the line +1 pinch salt, press V and then s. Only that line is staged.
  7. Press c c, type Add salt to the scones, press C-g and C-c C-c. The change to the flour is still waiting under Unstaged changes.

15.4.1 Changing the last commit

Everyone commits and then sees a spelling mistake. The commit menu has three ways to change the last commit, as long as you have not pushed it yet.

nonec eExtend. What is staged goes into the last commit, with the message as it is.

Use extend when you forgot a file, reword when the message is wrong, and amend when both need fixing.

The full menu has two more, for a mistake further back. c f (fix up) and c s (squash) make a small commit that is marked as belonging to an earlier one you pick. A later rebase with the switch - q folds it into that commit. Rebasing is described below.

15.4.2 Signing commits

A signed commit carries proof that it was made with your key, so that others can check it came from you. Tuatara commits the way git does with your own settings, signing included. There is nothing to switch on in Tuatara. You tell git once, in a terminal, which key to use and that every commit is to be signed:

git config --global user.signingkey YOUR-KEY
git config --global commit.gpgsign true

From then on C-c C-c in a message buffer makes a signed commit. Git's own manual describes the kinds of key it accepts. A tag can be signed as well: in the tag menu, turn on - s before you make the tag.

Signing and signing off are different things. The switch - s in the commit menu only adds a line of text to the message.

To see which commits are signed, press ! in the status and type log --format"%h %G? %s". A =G before a subject means a good signature and an N means none.

15.6.2 Merging

When the work on a branch is done, you merge it into main. Check out main, then press m m and name the branch. Git joins the two lines of work and makes a commit that records the join. Figure 15.3 shows the shape.

15.7 The stash

Sometimes you are half way through a change and need the files clean for a moment, for instance to check out main and fix a typing mistake someone pointed out. The work is not ready for a commit. The stash is a shelf for it. z z asks for a short message, puts every change aside and returns the files to the last commit. The stash appears in the status under Stashes.

When you come back, z p (pop) puts the changes into the files again and takes the stash off the shelf. z a (apply) does the same and keeps the stash, for when you want the changes on two branches. z d drops a stash without applying it, and that cannot be undone.

If the files changed in the meantime in the same places, popping can end in a conflict. Tuatara then keeps the stash and says so, and nothing is lost.

New files that git does not track yet are left where they are unless you turn on the switch - u first.

The full menu adds z i, which stashes only what is staged, z x, which stashes everything and leaves the staged part in place, z v, which shows what a stash holds, and z b, which makes a new branch out of a stash.

  2. Press z z, type serving note and RET. The change is gone from the file, and the status has a section Stashes.
  3. Press RET on the stash to see what it holds, then q.
  4. Press z p and pick the stash. The line is back in the file and the section Stashes is gone.

15.8 Merge conflicts

A conflict happens when two lines of work changed the same lines of a file. Git cannot know which is right, so it stops and asks you. It can happen in a merge, a rebase, a cherry-pick, or when a stash comes back.

Nothing is broken when this happens. The status says what git is doing on its Doing: line, with the keys that go on or stop, and it lists the files in question first, in a section called Unmerged files. Each line says how the two sides differ, for example both changed.

Git writes both versions into the file, between marker lines:

<<<<<<< HEAD
2 cups flour
=======
300 g flour
>>>>>>> metric

The lines after <<<<<<< are the first side. In a merge that is the branch you are on. The lines after the row of equals signs are the second side, the branch being merged in.

To settle a conflict, follow these steps.

  1. Press RET on the file in the status. It opens with the cursor on its first conflict, with the two sides coloured.
  2. For each conflict, decide. C-c ^ u keeps the first side, C-c ^ l the second and C-c ^ a both. C-c ^ n goes to the next conflict. You can also edit the lines by hand and delete the markers. Chapter 13 describes these keys in full.
  3. Save the file with C-x C-s.
  4. Press C-x g and then s on the file. Staging it tells git the file is settled, and it moves to Staged changes.
  5. When no file is left under Unmerged files, finish: m c commits a merge, R c goes on with a rebase, and A c with a cherry-pick.

If you would sooner not deal with it now, m a stops a merge and puts the branch and the files back as they were before it began. R a and A a do the same for a rebase and a cherry-pick. Each asks first.

Try it, with a conflict made on purpose

  1. In the status of ~/recipes, press b c, type grams and RET RET. In scones.txt change the flour line to 300 g flour. Save, press C-x g, stage with s and commit with c c and the message Flour in grams.
  2. Press b b, type main and RET. In scones.txt, run M-x revert-buffer if the line still says grams, then change it to 2 cups plain flour. Save, stage and commit as Say which flour.
  3. Press m m, type grams and RET. The merge stops. The status shows a Doing: line and scones.txt under Unmerged files.
  4. Press RET on the file. If the line says 2 cups plain flour and has no markers, the buffer is the old one: run M-x revert-buffer. Both versions are there between the markers. Press C-c ^ l to keep 300 g flour, then C-x C-s.
  5. Press C-x g, then s on the file, then m c. If a message buffer opens, press C-c C-c. The merge is done.

15.9 Rebase, cherry-pick, revert and reset

These four change or reuse commits that already exist. You can work for a long time without them. They are here for the day you need one.

15.9.1 Rebase

Rebasing makes your commits again on top of another commit, as if you had started your work later than you did. The usual reason is that main moved on while you worked on a branch. A merge would join the two with an extra commit. A rebase gives a single straight line instead, which many people find easier to read. R e asks what to rebase on, and R u rebases on the branch's upstream.

If one of your commits clashes with the new base, the rebase stops with a conflict. Settle it as described above and press R c to go on. The full menu's R s leaves that commit out, and R a stops the whole rebase and puts everything back.

R i rebases as a list says, and is the tool for tidying your own commits before you share them. It asks which commit to start after, then shows the commits after it in a buffer, one per line, the oldest first:

pick 81d04e7 Add the pavlova
pick 5c2e9a1 Fix a typo in the pavlova
pick 9b7f310 Add the bread

Change the list to say what you want. Move a line to change the order. Change the word pick to reword to give the commit a new subject, to squash or fixup to fold it into the commit on the line above, or to drop to leave it out. In the example, changing the second line to fixup makes the typo fix part of the commit that added the pavlova. C-c C-c rebases as the list says, asking for each new subject first. C-c C-k gives the list up and nothing changes.

One rule keeps you out of trouble: rebase only commits you have not pushed. A rebase makes new commits in place of the old ones, and anyone who already has the old ones would be left with a history that no longer matches yours.

15.10 Pulling and pushing

A remote is a second copy of the repository that you exchange commits with. It may be on a hosting service, on a server at work, or in a folder on a shared drive. A repository you copied from somewhere with git clone already has one, called origin. To give a repository of your own a remote, press M a in the status. It asks for a name, and origin is the custom for the first, then for the address.

Three verbs cover the exchange.

Fetch downloads the commits the remote has and you lack, and changes nothing in your files or your branch. It is always safe. f u fetches from the upstream's remote and f a from every remote. Afterwards the second line of the status says how far behind you are.

Pull fetches and then brings the new commits into your branch. F u pulls from the upstream. With no switch it only moves your branch forward when that is all there is to do. If you and the remote both have new commits, it stops and tells you, and you choose: - r before u rebases your commits on theirs, and - m merges theirs into yours. Tuatara never makes a merge you did not ask for.

Push sends your commits to the remote. P p pushes the branch to its upstream. The first time, the branch has no upstream yet: press P, turn on - u, then press e and name the remote. From then on P p is enough. If the remote has commits you lack, the push is refused. Pull first, then push again.

Fetching, pulling and pushing run in the background, so you can go on working. The sign P at the front of the mode line is lit while they run (chapter 11).

A forced push, - f or - F, replaces what the remote has with what you have. It always asks first, since it can remove other people's commits from the remote. Of the two, - f is the careful one: it refuses if the remote has something you have not seen. - n only tries, and reports what a push would send.

Tuatara does not ask for passwords itself. With an address that uses ssh, your keys come from the ssh agent of your system. If the server refuses, Tuatara shows git's own words.

The remote menu looks after the remotes themselves: M a adds one and M u gives one a new address. The full menu also renames, removes, and forgets branches that the remote has deleted.

15.13 Repositories you only look at

Git can be told by a repository to run programs: hooks, filters and other helpers named in the repository's own settings. That is fine in a folder of your own and unwise in one a stranger sent you. For this reason the status asks before it first opens a project, and one of the answers is l, look only.

In a look-only repository you can read the status, the log, diffs, blame and rewind as usual. The mode line of every git buffer says Look only. The keys that would change the repository are dimmed in the menus, and pressing one says why it is refused. A repository that holds evidence is always look-only.

Chapter 12 explains the question, how look-only reading works, and M-x trust-project, which asks again when you have changed your mind.

15.14.5 Patches and bundles

A patch is a commit written out as a file, to send to someone by mail or on a stick. In the patch menu, W c writes commits as patch files and W a applies a patch file to your files. The full menu's W s saves your uncommitted changes as a patch. The menu under w takes patch files in as commits, with their authors and messages: w w starts, and w c and w a go on or stop when one does not fit.

15.14.6 Repositories inside repositories

A submodule is another repository kept in a folder of yours at one exact commit, such as a theme that your website uses and someone else maintains. o opens its menu: o a adds one, and o u checks them all out after you have cloned a repository that has some.

A subtree also brings another repository into a folder, but copies its files into your own history, so that people who clone yours need nothing extra. O opens its menu.

A sparse checkout goes the other way. It shows only some folders of a large repository in your files and leaves the rest in the history. > opens its menu: > s chooses the folders and > d brings everything back.
